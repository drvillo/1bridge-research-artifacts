# Governance research traceability and publication limits

Examined 16 October 2026 against public primary sources and the revisions in the [repository map](governance-repository-map.md). This map connects the four manuscript tracks with implementation evidence. The cited research describes mechanisms and prior systems; it does not prove this composition secure or substitute for independent review.

| Research source | Mechanism relevant to 1Bridge | Current implementation evidence | Publication-safe claim and limit |
|---|---|---|---|
| [CONIKS, USENIX Security 2015](https://www.usenix.org/conference/usenixsecurity15/technical-sessions/presentation/melara) | Independently monitored key bindings and anti-equivocation motivate authenticated authority state. | `1bridge-authority/src/authority-lifecycle.ts` and the app's signed actor-binding/recovery paths; the app's customer-held anchor pin is separate from publisher retrieval. | Cite as prior key-transparency work. 1Bridge does **not** implement CONIKS's privacy-preserving directory or its global non-equivocation guarantee. A retained pin and external comparison are assumptions, not automatic enrollment identity proof. |
| [KATENA, Frontiers in Big Data 2026](https://www.frontiersin.org/journals/big-data/articles/10.3389/fdata.2026.1829960/full) | Client-verifiable governance transitions and append-only evidence motivate signed share, revocation and recovery workflows. | `1bridge-authority/src/action.ts`; app protected share/signing completions, optional operator-signed rotation and D4 reset paths. The compact observer checks only global registry extension. | Describe an implementation related to KATENA's architecture, with narrower observed coverage. Guest intake remains provider-recorded OTP-associated activity, not a guest-signed transition. This implementation does not establish a compromised-browser (T3) guarantee or KATENA's full architecture. |
| [RFC 9162, Certificate Transparency v2](https://www.rfc-editor.org/rfc/rfc9162.html) | Domain-separated Merkle leaf/node hashing, inclusion and append-only consistency proofs. | `1bridge-authority/src/history.ts` and `src/registry.ts` supply tested proof functions; the observer checks a signed registry head and consistency path. The app separately checks included `feed_anchor`/`feed_head` entries and signed feed continuation for a retained action receipt. | Claim RFC-shaped proof algorithms and a locally tested global registry witness. One included head proves only its signed prefix. The observer does not read action leaves, prove that an included head is latest, or detect a coherent withheld X→Y action from its root-only poll. No proof establishes publication of every business audit fact. |
| [RFC 9474, RSA Blind Signatures](https://www.rfc-editor.org/rfc/rfc9474.html) and [RFC 9576, Privacy Pass Architecture](https://www.rfc-editor.org/rfc/rfc9576.html) | Blind issuance/unblinding supports unlinkable proof-access token use at the cryptographic layer; Privacy Pass explains issuer/origin separation and anonymity-set metadata risks. | `1bridge-authority/src/blind-proof-access.ts`, `src/blind-proof-access-server.ts`; app atomic proof-access redemption and one-use state. | Claim a bounded RFC 9474-derived blind proof-access profile after verifying exact parameter/vector tests. Do not call the app a full Privacy Pass deployment or claim end-to-end anonymity: timing, account authentication, scope, key cohorts and network metadata can correlate issuance with redemption. |
| [RFC 4130, AS2](https://www.rfc-editor.org/rfc/rfc4130.html) | A signed receipt can bind a message identifier and content digest to a specific acknowledgment. | 1Bridge's signed action and publisher completion receipt bind operation/effect/leaf/checkpoint; app customer-held evidence compares later observer coverage. | Cite the **receipt-binding principle only**. A 1Bridge publisher completion receipt says a signed action was integrated under a publisher checkpoint; it is **not** an AS2 recipient-signed acknowledgment of receipt or reading. Recipient acceptance needs a separate actor and protocol. |
| [IETF Key Transparency Architecture draft](https://datatracker.ietf.org/doc/draft-ietf-keytrans-architecture/) | State loss, monitoring delay and third-party auditing inform pin/export and pending coverage semantics. | App independent pin/history export and observer comparison; public authority `src/history-export.ts` verifies a saved v1 file against a separately retained checkpoint without app API access; shared observer autonomous pull. | Cite a dated draft revision, not an RFC. Offline verification authenticates the exported prefix and its retained predecessor, not current global freshness. An offline observer can jump across a published registry backlog with a valid consistency proof; a never-published coherent tail remains unknowable until an independently retained receipt or incompatible continuation surfaces. |

The four revised manuscripts remain at private application commit `49cbc09b` on the `codex/research-publications` branch for authorized review. `research/1bridge-vault-encryption-research.tex` separates baseline key wrapping and access-key delivery from later protected shares, authority, recovery and blind proof access. `research/1bridge-vault-system-companion.tex` maps D1–D4 to routes and states, including unsigned operational paths. `research/1bridge-guest-submission-protocol.tex` distinguishes its experimental guest-signed prototype from deployed OTP intake and describes the later governance protocol. `research/1bridge-vault-benchmark-report.tex` separates original browser and activation samples from the public [authority-history summary](../results/governance-authority-history-20261016.json) and [synthetic registry-proof measurements](../results/governance-compact-registry-proof-20261016.json). Public readers can inspect the evidence files here; manuscript source access requires authorization to the application repository.

Publication gates still open: reconcile each manuscript assertion with the final application revision and deployed outcomes, run a nonempty Next-to-independent-observer smoke and representative Vercel timings, obtain independently delivered publisher/observer pins, and obtain independent technical review before presenting the work as a peer-reviewed 1Bridge result. The current benchmark files do not measure a deployed service; the authority-history JSON has aggregate statistics but no raw sample values. A standards conformance test or a cited peer-reviewed paper does not constitute a formal correctness proof of this composed system.
