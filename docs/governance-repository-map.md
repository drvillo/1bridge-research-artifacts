The shared observer has no customer-specific token, feed list or receipt ingress. A customer compares an independently pinned observer report with a registry inclusion proof for a `feed_anchor` and an included advertised `feed_head`, then verifies the retained action receipt against authenticated feed continuation. That proves the particular action in that included prefix. It does not prove that the included head is the latest for the customer or that every product audit event was published. An observer outage leaves operations and releases available. Enterprise/Government strict mode applies a 24-hour freshness rule to **audit review**, without delaying a release. A future customer-operated observer is a separate deployment profile.

The current evidence classes are library vectors, app route/transaction tests, observer persistence/catch-up tests, a local two-feed reader-to-observer HTTP run, a local nonempty Next-to-observer wire smoke, and the pinned synthetic proof benchmark. A deployed third-party observation and production latency measurement are still absent. Cite the exact class that supports each manuscript statement.

The one default observer profile is installed by the deployment operator: the observer's public key and origin, registry publisher public key and signed registry genesis. Its private signing key stays with the independent observer. Workspace admins see the public values without editing them. Enrollment combines those values with the locally prepared dual-signed workspace anchor in a public trust file, confirmed saved separately from the encrypted recovery kit. Later devices import that file; server refresh does not silently replace retained trust. This improves setup without removing the T2 honest-client and first-contact authentication assumptions.

The same effective capability feeds navigation, setup and action controls; server writes recheck it under the billing coordination used by plan changes. Current actor eligibility, recipient binding and root rotation remain separate from the commercial gate. A true routine holder can review member bindings before their own actor is activated; a root-free admin-only custodian is not routed through that ceremony. Observer outages affect audit review, never product releases. These are additive application properties, not changes to the public library's cryptographic primitives or to the compact observer's scope.

At the later unmerged app branch revision [`f44a051a`](https://github.com/drvillo/ubo-guard/tree/f44a051a2539a2be930ad55f218002b25a9cd104), `webapp/src/lib/authority/registry-source.ts` calls `buildRegistryConsistencyProof` and verifies the result against signed checkpoint roots. `registry-merkle.ts` asks for the proof's range hashes; `registry-node-store.ts` obtains indexed leaf hashes or completed aligned subtree hashes from `authority.registry_entries` and `authority.registry_merkle_nodes`, recursively combining a nonaligned remainder. The [Merkle-node migration](https://github.com/drvillo/ubo-guard/blob/f44a051a2539a2be930ad55f218002b25a9cd104/webapp/prisma/migrations/20261020160000_authority_registry_merkle_nodes/migration.sql) provides the `(start_index, height)` primary key. Existing unit/integration tests cover bounded lookups and proof correctness, but their assertions are not measured application/SQL latency or memory at scale. The new runner measures this source path when executed with the pinned private checkout and a dedicated local database; publication of results requires retaining its raw artifact and environment provenance.
