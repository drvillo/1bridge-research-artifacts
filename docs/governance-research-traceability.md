# Governance research traceability and publication limits

Examined 15 October 2026 against public primary sources and the revisions in the [repository map](governance-repository-map.md). This is a source-to-claim plan for the final article update, not a formal proof of 1Bridge or an independent peer review. The named papers and RFCs establish mechanisms or comparisons; each 1Bridge property still needs the implementation evidence shown below.

| Research source | Mechanism relevant to 1Bridge | Current implementation evidence | Publication-safe claim and limit |
|---|---|---|---|
| [CONIKS, USENIX Security 2015](https://www.usenix.org/conference/usenixsecurity15/technical-sessions/presentation/melara) | Independently monitored key bindings and anti-equivocation motivate authenticated authority state. | `1bridge-authority/src/authority-lifecycle.ts` and the app's signed actor-binding/recovery paths; the app's customer-held anchor pin is separate from publisher retrieval. | Cite as prior key-transparency work. 1Bridge does **not** implement CONIKS's privacy-preserving directory or its global non-equivocation guarantee. A retained pin and external comparison are assumptions, not automatic enrollment identity proof. |
| [KATENA, Frontiers in Big Data 2026](https://www.frontiersin.org/journals/big-data/articles/10.3389/fdata.2026.1829960/full) | Client-verified signed governance artifacts and logged share/revocation/rotation workflows motivate the composition. | `1bridge-authority/src/action.ts`, `src/replay.ts`; app signed-share completion and D4 reset paths; observer replay. | Describe an implementation **inspired by** KATENA's architecture. Current 1Bridge signing-package/intake and operator-signed rotation coverage are incomplete. The article does not certify this implementation or solve a compromised provider-served browser. |
| [RFC 9162, Certificate Transparency v2](https://www.rfc-editor.org/rfc/rfc9162.html) | Domain-separated Merkle leaf/node hashing, inclusion and append-only consistency proof shapes. | `1bridge-authority/src/history.ts`; frozen vectors and adversarial replay tests in the library; signed source checkpoints and observer replay. | Claim RFC-shaped tree/proof implementation and tested vectors, with an independently accepted root **and size**. RFC 9162 proof algorithms alone do not guarantee that all business events were logged or that one publisher did not serve an unseen coherent tail. |
| [RFC 9474, RSA Blind Signatures](https://www.rfc-editor.org/rfc/rfc9474.html) and [RFC 9576, Privacy Pass Architecture](https://www.rfc-editor.org/rfc/rfc9576.html) | Blind issuance/unblinding supports unlinkable proof-access token use at the cryptographic layer; Privacy Pass explains issuer/origin separation and anonymity-set metadata risks. | `1bridge-authority/src/blind-proof-access.ts`, `src/blind-proof-access-server.ts`; app atomic proof-access redemption and one-use state. | Claim a bounded RFC 9474-derived blind proof-access profile after verifying exact parameter/vector tests. Do not call the app a full Privacy Pass deployment or claim end-to-end anonymity: timing, account authentication, scope, key cohorts and network metadata can correlate issuance with redemption. |
| [RFC 4130, AS2](https://www.rfc-editor.org/rfc/rfc4130.html) | A signed receipt can bind a message identifier and content digest to a specific acknowledgment. | 1Bridge's signed action and publisher completion receipt bind operation/effect/leaf/checkpoint; app customer-held evidence compares later observer coverage. | Cite the **receipt-binding principle only**. A 1Bridge publisher completion receipt says a signed action was integrated under a publisher checkpoint; it is **not** an AS2 recipient-signed acknowledgment of receipt or reading. Recipient acceptance needs a separate actor and protocol. |
| [IETF Key Transparency Architecture draft](https://datatracker.ietf.org/doc/draft-ietf-keytrans-architecture/) | State loss, monitoring delay and third-party auditing inform pin/export and pending coverage semantics. | App independent pin/history export and observer comparison; public authority `src/history-export.ts` verifies a saved v1 file against a separately retained checkpoint without app API access; shared observer autonomous pull. | Cite a dated draft revision, not an RFC. Offline verification authenticates the exported prefix and its retained predecessor, not current global freshness. An offline observer can catch up on published backlog, while a never-published coherent tail remains unknowable until an independently retained receipt or incompatible continuation surfaces. |

The original encryption description can add the authority, recovery and blind-token keys to its key-role table without implying that document encryption changed. The system companion should trace the exact share/observer/recovery journeys and identify unsigned operational paths. The protocol manuscript should state the signed statement, effect opening, predecessor, Merkle checkpoint, independent pin and guest bootstrap assumptions. The benchmark report must measure the implemented library, observer catch-up and app flows at pinned commits; the old `webcrypto-seal` measurements remain a separate baseline.

Publication gates: obtain the pending product choices, finish and verify the affected D1–D4 code, freeze source commits, collect raw repeatable governance measurements, reconcile each assertion with code and executed tests, update all four `.tex` sources, compile and inspect PDFs, and obtain independent technical review before presenting the work as a peer-reviewed 1Bridge result. A standards conformance test or a cited peer-reviewed paper does not constitute a formal correctness proof of this composed system.
